# События об изменении и архивации задачи рождает сервер, а не клиент

`notify-updated` и `notify-deleted` позволяли клиенту самому решать, когда возникло Событие, и самому писать его текст: `card_id`, `board`, `card_title` и список правок приходили от клиента и не сверялись с БД, а `dedupe_key` строился из этих же полей — подделка обходила дедупликацию (AUDIT-006). Любой аутентифицированный участник семьи мог отправить push с произвольным текстом от имени чужой задачи. Мы переносим порождение `card.updated` и архивации на сервер, в те же операции, что меняют задачу: `PATCH`/чек-лист/дедлайн/исполнитель/приоритет/подзадачи/вложения теперь сами создают Событие транзакционно с изменением. Правки одного человека за один непрерывный сеанс редактирования схлопываются в одно Событие — окно ключуется по `(card_id, actor_id)` и продлевается по паттерну `CardDeadlineReminder.scheduled_at`: реально уходит диспетчеру либо по пустому сигналу-триггеру `notify-updated` при закрытии экрана задачи (без данных — только «сейчас»), либо через 5 минут тишины как страховка от упавшей вкладки. Текст push намеренно обобщён — «В «{название}» сделаны изменения», без перечисления конкретных правок: детальная разбивка по полям — это будущая лента событий, вне рамок этого решения. Архивация получает отдельный тип `CARD_ARCHIVED` вместо жёстко зашитого на клиенте текста «Удалена задача» через `CARD_DELETED` — термин «В архиве» (не «удалена») уже был зафиксирован в [CONTEXT.md](../../CONTEXT.md) до этого решения, просто код ему не следовал. `CARD_DELETED` для задач остаётся неиспользуемым: жёсткого удаления одной задачи из архива сегодня не существует как функция.

## Considered Options

- **Точечный патч**: сверять `card_id`/`title` из запроса клиента с БД, не меняя источник события. Отклонено — правило «когда уведомлять» осталось бы размазанным между UI и сервером, а не только в одном месте, и провокацию произвольного текста это не убирает, только вводит верификацию задним числом.
- **Чистый дебаунс без сигнала от клиента**: событие всегда уходит через N секунд тишины, независимо от закрытия экрана. Отклонено — момент закрытия экрана является надёжным сигналом времени (не содержимого), и превращать мгновенную сегодня доставку в гарантированную N-секундную задержку без причины means перебираем в другую сторону.
- **Событие на каждую правку поля без схлопывания**: проще всего реализовать, но превращает один сеанс редактирования (название + дедлайн + чек-лист) в несколько push подряд; единственный клапан — полностью замьютить `card.updated`. Отклонено как разменивающее полезность уведомления на техническую простоту.

## Consequences

- В outbox появляется второй случай отложенной, а не немедленной доставки строки (`NotificationEvent`, аналогично `CardDeadlineReminder.scheduled_at`); опрос диспетчера должен уметь пропускать ещё не созревшие строки этого типа так же, как он уже делает для напоминаний.
- Коалесация ключуется по актору, а не только по задаче: если двое членов семьи одновременно редактируют одну задачу, это два отдельных События/push, а не одно смешанное — авторство правки остаётся однозначным.
- Автор правок по-прежнему получает push о своих же изменениях (в отличие от комментариев) — намеренно: уведомление о правке, которую человек не помнит, что делал, — сигнал компрометации аккаунта или входа под его логином другим членом семьи.
- `notify-updated` не удаляется, вопреки буквальной рекомендации аудита «клиентские эндпоинты уведомлений удалить после переноса» — он остаётся как безопасный триггер без тела (только «flush сейчас» для своего же окна), потому что источником текста он больше не является. `notify-deleted` удаляется полностью — на него не завязан ни один клиент, включая замороженное Android-приложение.
- Текст push и детальный список правок расходятся: `payload` продолжает нести структурированные данные о том, что именно поменялось, но пользователю в push это не показывается. Пока не построена лента событий с детальным рендерингом, это состояние — не баг, а осознанно отложенная часть работы.
